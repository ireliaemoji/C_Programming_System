## 已证实问题与根因

1. B-ENV-02 首次启动失败：tools/start-local.ps1 对 docker compose ps -q mysql 的空输出直接 .Trim()。无既有容器时 PowerShell 得到 null，尚未进入端口冲突保护就异常；A 验收提交也有相同代码。B 首次实际复现，先手动 compose up 绕过。建议 A 将结果转字符串后 Trim，并在无容器现场复验。
2. B-ENV-03 Unity 假阴性：Find-Unity 未覆盖 C:\Program Files\Unity 2022.3.62f3c1\Editor\Unity.exe；且每个通配候选仅取第一个版本后比较。B 本轮环境检查实测退出 1，实际指定编辑器已成功运行。建议 A 枚举全部候选和常见版本化安装目录，再按版本筛选。
3. B-ENV-04 SDK 安装缺口：安装脚本仅 dotnet 命令不存在才装 SDK；已有 SDK 8 时不会自动安装 10。本轮显式 winget 已补齐。建议 A 按目标 SDK 是否存在判安装需求。
4. 本机 3306 确有 mysqld PID 6376/7696 监听；项目改用 13306 后成功，未停止原有服务。其余实例的用途与数据归属未检查，不能认定可删除。

## 数据位置与迁移

当前链路：Unity -> 本机 Windows API -> 127.0.0.1:13306 -> Docker MySQL 8.4.9。挂载实测为 volume c_program_system_c_exam_mysql_data -> /var/lib/mysql。数据最终占用本机磁盘，由 Docker Desktop 的 Linux 环境管理，并非仓库内原生 MySQL 数据目录，也不随 Docker 账号同步。volume 持久化不等于备份。

沿用已确认方案：A/B 各有独立库。日常同步 Git 中的版本化结构迁移和无敏感种子数据，不复制 A 全库或 .env。当前无业务表，测试表已清理，目前无需迁移业务数据。

后续确需换机或搬到正式服务器：先确定来源与目标版本，备份并验证恢复；使用 mysqldump 等逻辑导出应用库到受控文件，再导入独立目标库、执行结构迁移，核对记录数/关键数据和应用功能后才切换连接；保留原库与回退方案。InnoDB 可按需求使用 --single-transaction，并避免导出期间并发 DDL。不要复制运行中的 /var/lib/mysql，不提交真实备份/密码，不执行 down -v。数据库大版本升级须单独验证兼容性，不能直接换镜像试运行。

参考：https://docs.docker.com/engine/storage/volumes/ ；https://dev.mysql.com/doc/refman/8.0/en/mysqldump.html 。上述迁移为建议流程，尚未执行备份/迁移演练。
