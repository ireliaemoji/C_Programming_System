# 多电脑访问、数据迁移与安全边界

更新日期：2026-11-19
状态：已确认未来数据源安排；另一台电脑尚未部署，远程访问尚未实施。

## 已确认的部署方向

另一台个人电脑作为部署机 B，由 B 上的 Docker MySQL 保存唯一正式使用的开发数据。本机 A 通过 B 上的 ASP.NET Core API 使用这些数据。Unity 永远不直接连接 MySQL，也不保存数据库连接密码。

```text
电脑 A：Unity 客户端
          ↓ 受限网络中的 HTTPS API
电脑 B：ASP.NET Core API
          ↓ 本机回环地址或 Docker 内部网络
        Docker MySQL
          ↓
        B 上的 named volume
```

API 可以先作为 B 上的进程运行，后续也可容器化；不要求 Unity 所在电脑运行本地 API 或 MySQL。B 需要开机、联网，并保持 API、Docker 和 MySQL 正常运行。休眠、关机、重启或断网都会影响 A 的访问。

目前仍使用 A 上的本地原生 MySQL。只有在 B 完成迁移和验收后，才将 B 标记为唯一数据源并切换 A 的 API 地址；这份文档没有执行迁移、开放端口或卸载本地软件。

## Docker 与数据同步的关系

- Docker Desktop、容器和 named volume 均属于部署它们的电脑。两台电脑使用相同 Compose 文件或卷名，不会共享或同步数据。
- Git 保存代码、Compose 配置、数据库结构迁移和无敏感信息的演示数据，不保存实际数据库文件、备份、密码或用户答卷。
- B 成为唯一数据源后，A 通过同一个 API 访问同一份数据，不需要每次换电脑都重新导入。
- A 单独启动自己的 MySQL，只会得到另一份独立数据。不要把 A、B 两个数据库同时当作可写主库，以免形成两份不一致的数据。

## 数据应放在哪里

| 内容 | 位置与处理 |
|---|---|
| B 上的 MySQL 数据文件 | B 的 Docker named volume，挂载到 `/var/lib/mysql`；存储由 Docker 管理 |
| 数据库备份 | volume 外的独立目录，并保留另一份加密副本；限制访问权限，验证可恢复 |
| 表结构、迁移、演示数据 | Git 仓库；不得包含真实账号、邮箱、答卷、成绩或密钥 |
| API/数据库凭据 | 部署机环境配置或机密配置；不得提交 Git、写入 Unity 或输出到日志 |
| A 当前数据库 | 暂保留在 `%LOCALAPPDATA%\CExam\mysql-data`，迁移成功前不删除 |

Named volume 提供持久化，但不等于备份。删除卷、`docker compose down -v`、Docker 清理/重置、磁盘损坏仍可能导致丢失。不要用文件同步软件直接同步正在运行的 MySQL 数据目录。

## 首次迁移到 B

1. 确认 B 的系统、Docker 引擎、磁盘空间、MySQL 目标版本和连接网络。
2. 暂停 A 的业务写入，用 MySQL 官方逻辑备份工具导出 `c_exam`，通过加密通道或受控介质传输。备份不提交 Git。
3. 在 B 创建独立 volume 和数据库账号，设置新的随机密码。导入备份前核对目标库，避免覆盖已有数据。
4. 检查表、记录、中文编码和应用连接，进行一次备份恢复演练。
5. 启动 B 的 API，先在 B 验证 `/health`，再完成认证、传输加密和网络限制后允许 A 访问。
6. 将 A 的 API 地址由 `localhost` 改为 B 的受限网络地址，在 Unity 验证读取与后续写入；确认所有写入都落在 B。
7. 停止 A 的旧数据库并保留备份，记录切换时间和回退方式，再将 B 标记为唯一数据源。

当前 A 安装的是 MySQL 8.4.9，而仓库 Compose 使用 `mysql:8.0`，版本尚未统一。迁移前需要确定并固定兼容版本；不能把 8.4 的原始数据文件直接复制给 8.0 使用，也不能假定逻辑导出可以无条件向旧版本导入。此次仅记录问题，不修改当前版本。

## 个人电脑部署是否会泄露数据

个人所有权不等于网络隔离。部署本身不意味着数据必然泄露，但开放端口、无认证 API、泄露密码、恶意软件或错误挂载都会造成风险。当前没有做入侵取证，不能据此宣称从未发生泄露。

访问路径按实际网络选择：

- 同一可信局域网：仅允许指定客户端访问 API，配置防火墙范围；不要向整个网络开放数据库。
- 不同网络：优先使用只授权自己设备的私有 VPN，并限制设备访问规则；VPN 仍需要保护账号和设备，不能代替 API 身份认证。
- 当前不进行路由器公网端口转发，不直接公开 MySQL、Docker 管理接口或当前开发 API。如以后需要公开服务，另做部署与安全验收。

B 上的最小安全要求：

| 项目 | 必须满足的边界 |
|---|---|
| MySQL 端口 | API 在宿主机运行时仅发布 `127.0.0.1:3306:3306`；API 容器化时优先仅使用容器内部网络，不发布 MySQL 端口 |
| MySQL X Protocol | 不发布 33060；不用时禁用 |
| API | 仅绑定/允许所需网络；远程访问使用可信 HTTPS 和身份认证，不通过跳过证书校验解决连接问题 |
| 授权 | 后续学生/教师功能必须在服务端校验角色和数据归属，VPN 登录不等于业务授权 |
| 密码 | 替换仓库示例密码；应用不用 root，账号按所需权限配置；迁移后停用临时空密码 root |
| 容器权限 | 不挂载个人文档、整个用户目录或 Docker socket，不开启特权容器 |
| 主机和备份 | 保持系统更新，限制其他本机账号和备份访问，保留可恢复的加密备份 |
| 日志 | 不输出数据库密码、令牌、完整答卷等敏感数据；远程接口不返回内部异常详情 |

容器只访问显式挂载目录并不意味着主机绝对安全；主机管理员权限、Docker 管理权限或应用漏洞仍可能影响数据。因此 B 也应视为需要维护的服务器。

## 当前配置尚不能直接作为共享部署配置

- `docker-compose.yml` 仍使用 `3306:3306`。Docker 默认将这种端口发布到所有宿主机地址；部署到 B 前必须限制为回环或改用容器内部网络。
- Compose、API 配置和工具中的密码是公开示例值，不能用作 B 的实际密码。
- 当前原生开发 MySQL 通过 `--initialize-insecure` 初始化，root 未设密码；即使仅回环访问，也不能将其直接开放为远程数据库。
- 当前 API 只有健康检查，未实现业务认证和权限控制。当前 HTTP localhost 探针验证不等于远程安全验收。
- `tools/check-environment.ps1 -InstallMissing` 仍会安装原生 MySQL。采用 B 的 Docker 方案前应调整工具：B 检查 Docker/容器，A 不要求安装 MySQL；此次未更改工具行为。

## 部署前需要用户补充的信息

- B 的操作系统、Docker 是否可运行，以及 A/B 是否在同一网络。
- 只自己开发使用，还是未来让其他教师/学生访问。
- 网络访问采用局域网还是私有 VPN；选择远程访问方式后再配置实际地址、证书和访问规则。
- 备份保存位置及是否存在需要迁移的真实数据。

目前无需提供数据库密码、管理员密码或路由器凭据。需要人工辅助时，主要是操作系统管理员授权、必要重启以及网络设备/设备账号的授权操作。
